## git diff` pour voir ce qui a changé

Donc revenons à notre dépôt pour se rappeler notre dernier changement a été d'ajouter une ligne à `readme.md`. La commande `:information_source:` nous donne la liste de changements, n'est-ce pas? L'avant dernier commit c'est **817c439** et nous pouvons maintenant voir ce qui a changé.

La commande:

```console

```
Nous dira quelque chose comme:

> :information_source:
> Git à la différence d'autres systèmes de gestion de version ne conserve pas une chaîne de modifications... mais bien des vrais instantanés de chaque fichier. Quand nous voyons le "diff" la différence entre deux états d'un fichier il calcule cela à la volée. Mais comme nous l'avons noté plus haut.. Git sait être très intelligent et bien compresser les choses, avec **git-pack** qui est un format super-futé et terriblement optimal -- d'ailleurs c'est une des raisons pour lesquelles Git est si rapide. Mais ceci est un détail interne d'implémentation qui n'a pas d'effet sur votre usage de l'outil et donc hors du cadre du présent cours: nous allons aussi profondément qu'il le faut pour comprendre ce que l'on fait, précisément. Mais pas plus.

## git diff --cached` pour voir ce que l'on a ajouté à l'index

Une fois qu'on a ajouté des chose à l'index, à notre **staging**, `git diff` va plus rien nous dire. Si bous voulons voir les changements qui sont prêts au **commit**... `git diff --cached` est notre ami. 


## es différences avec le dernier commit ...

Nous avons vu comment utiliser `git diff` avec le **SHA** d'une révision mais Git nous fournit aussi une syntaxe agréable pour parler en temps relatifs. Par exemple `git diff HEAD~1` est une manière de dire: donne moi le **diff** avec le commit précédent. `git diff HEAD~2`, vous l'auriez compris nous montre la différence avec l'avant dernier commit.

Voilà le **log** qui est la même chose .. sauf une petite chose: là où en haut on avait **(HEAD -> master)**, maintenant **dc5139** est marqué comme **master** et **817c43** comme **HEAD**. De quoi s'agit-il ?

**HEAD** c'est un pointeur vers là où on est actuellement. On était sur le commit **dc5139c** et maintenant notre zone de travail est, dans le passé sur **817c43**. 

Si maintenant on fait `git checkout master` le pointeur **HEAD** va à nouveau se positionner sur notre tout dernier commit celui qui a le message "added git log command". Nous pouvons le vérifier avec `git log` ou `git log --branches` (qui là, donc vont faire précisément la même chose).

Mais c'est bizarre, on a appris à faire `git checkout {sha}` et maintenant nous au lieu de mettre plein de caractères bizarres on écrit en toutes lettres **master**.

Donc c'est quoi **master** ? **master** est une branche. Nous vous l'avons déjà raconté à l'introduction, avec Git nous pouvons travailler non seulement sur des révisions comme une seule flèche temporelle ... mais sur des multiples versions différentes, en même temps. **master** ou _maître_ en Français est comme son nom l'indique: la version maîtresse, le haut de l'arbre. Un peu plus tard nous allons vous montrer comment créer d'autres branches, comment utiliser `git checkout` pour sauter de l'une à l'autre, pour le moment restons avec un seul tronc.

> :information_source:
> Dans d'autres système de gestion de version, comme les vénérables CVS ou SVN cette branche maîtresse s'appelait en effet "Trunk" ou en Français "tronc" ce qui donne bien l'image de cette branche principale de laquelle toutes les autres sortent. Pour Git c'est une simplification, il est si puissant et malléable que ce concept est réducteur ... mais voilà, on va pas trop se compliquer la vie toute-de-suite. Imaginez donc **master** comme le tronc principal. 

Comme c'est le cas pour **HEAD** une branche est simplement un pointeur vers un **commit**. Et souvent le **HEAD** pointe vers le haut de la branche sur laquelle on est. Comme nous sommes sur la branche **master**, **HEAD** pointe vers le "haut" de celle-ci. Notre dernier commit.

Nous aimons regarder sous les capot n'est-ce pas? regardons quelques autres structures de données à l'intérieur de notre cher `.git` pour être sûr de bien comprendre.

Assurez-vous d'avoir fait `git checkout master` et nous pouvons essayer les commandes suivantes

```console
cat .git/HEAD
```
Qui va nous sortir: 

```console
ref: refs/heads/master
```
Donc ceci est une référence, qui pointe vers `refs/heads/master` -- ce truc là, c'est aussi un fichier sous `.git`. Nous pouvons suivre la trace et taper:

```console
cat .git/refs/heads/master
```

Et il va nous répondre par le **SHA**, le **commit-id** de notre tout dernier commit:

```console
dc5139c9c77b0d2210301b3fdf68817311f57b2e
```

Un peu plus tôt quand nous avons fait `git checkout 817c439`, git a donné un gros message que nous avions choisi d'ignorer, lisons le maintenant:

```console

C'est qu'il nous dit là c'est en gros: hé vous avez choisi de faire un `checkout` non pas sur le haut de la branche, mais sur un **commit** spécifique. **HEAD**, la tête, le pointeur de l'état actuel est maintenant "détachée" de sa branche (retenez en Anglais "Detached head").

> :information_source: nous pouvons faire `git checkout {le-nom-d-une-branche}` car la branche est simplement un pointeur vers un **commit** donc `git checkout master` nous ramène à en haut de notre arbre, à notre dernier **commit**


## ous avons vraiment fait fausse route ? Recommencer au propre avec `git reset`

Nous avons pu revenir déjà dans le passé avec `git checkout` qui a mis notre zone de travail à l'état d'un commit précédent. Mais alors nous étions dans cet état un peu bizarre. Le **detached head**, ou HEAD ne pointait plus vers le haut de notre branche. Si nous le voulions nous pouvons revenir dans le passé de manière à ce que l'on puisse continuer à nouveau. 

Imaginons par exemple que toutes ces tergiversations autour de nom de notre répertoire `media` font du désordre dans notre historique, que cela n'apporte aucune valeur au lecteur futur de notre code. Ni le fait que nous avons ajouté le fichier LICENCE simplement pour l'enlever plus tard?

Notre historique actuelle est:
```console
* e3e73b4 - (4 months ago) Rename files to media                         - Ori Pekelman          (HEAD -> master)
* 9f49d65 - (4 months ago) Remove license file                           - Ori Pekelman
* 9911ff4 - (4 months ago) Add git log to the list of commands we lear.. - Ori Pekelman
* f645e6b - (4 months ago) Add .gitkeep so files will be added to the .. - Ori Pekelman
* 6dcbff3 - (4 months ago) Adding a license file                         - Ori Pekelman
* 2940f38 - (4 months ago) Add the list of commands we learned today.     - Ori Pekelman
* 5e8354a - (4 months ago) Added readme.md                               - Ori Pekelman
```

`git reset 2940f38` va remettre **HEAD** au niveau de ce commit, comme notre `git checkout`. Mais notre zone de travail, elle, reste dans son état actuel, un `git status` nous dira:
```console
On branch master
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git checkout -- <file>..." to discard changes in working directory)

	modified:   readme.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)

	media/

no changes added to commit (use "git add" and/or "git commit -a")```

Nous pouvons maintenant créer des nouveaux **commit**s, au propre:

```console
git add readme.md
git commit -m'Add git log to the list of commands we learned'
git add media
git commit -m'Add media directory with .gitkeep'
```

Maintenant notre historique est bien plus propre:

```console
* 2f13f45 - (4 months ago) Add media directory with .gitkeep              - Ori Pekelman          (HEAD -> master)
* 0809db1 - (4 months ago) Add git log to the list of commands we lear.. - Ori Pekelman
* bbde8c5 - (4 months ago) Add the list of commands we learnt today.     - Ori Pekelman
* 5e8354a - (4 months ago) Added readme.md                               - Ori Pekelman```

Dans ce cas nous avons voulu se remette à un état précédent tout en gardant les changements que nous avons fait. Mais qu'est-qui se passe si nous voulons vraiment se débarrasser de nos quelques derniers commits? nous pouvons faire un mise-à-zero dure avec `git reset --hard`. 

Ainsi `git reset --hard 5e8354a` va nous ramener à notre état initial, avec un seul fichier `readme.md` qui aura une seule ligne de contenu. Parfois s'est agréable de se débarrasser du poids du passé.

> :warning:  Nous le verrons plus bas que nous allons parler de collaboration, mais notons toute de suite quelque chose; Quand nous travaillons seuls, sur un dépôt à nous, sur une branche à nous, réécrire le passé est agréable et utile. Mais quand on aura commencer à travailler avec les autres nous n'aurons plus le même luxe. Le passé, c'est le passé. Nous avons d'autres commandes Git qui nous permettent d'annuler des choses en gardant une historique commune comme `git revert` que nous verrons plus tard.

## écapitulatif  voir et jouer avec l'historique

* `git log` nous permet de voir la liste des **commit**s dans le passé, la liste des révisions
* `git diff` nous permet de voir les changements introduits dans un **commit**
* `git blame` nous permet d'inspecter un fichier et voir quelle ligne a été modifié par quel **commit**
* `git show` nous permet d'inspecter un **commit**, mais aussi un **tree** ou un **blob**
* **master** est une branche de notre code, même la branche principale
* **detached head** c'est la situation dans laquelle notre pointer **HEAD** ne pointe pas vers le dernier commit d'une branche.
* `git checkout {commit}` nous permet de passer le pointeur du **commit* actuel de la zone de travail à un **commit** spécifique il change le pointer **HEAD** et il remet notre zone de travail à l'état qu'il avait lors de ce commit.
* `git reset {commit}` fait la même chose que `git checkout` mais remet aussi le haut de notre **branche** à ce commit en gardant les modifications dans notre zone de travail.
* `git reset --hard {commit}` fait la même chose en enlevant toutes nos modifications de la zone de travail
