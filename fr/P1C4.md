###  Sauvegardons notre travail!

Nous avons pris le parti pris de tout faire très, mais très lentement en vous expliquant chaque étape du chemin. Mais on vous a aussi promis de la simplicité. Donc.. imaginons qu'on a un projet, qui n'est pas encore sous contrôle de Git (appelons le `my_existing_project`) qui contient nos fichiers code source. Comment les mettre sous contrôle Git simplement et rapidement? 

Rien de plus simple:
```console
cd ~/projects/my_existing_project
git init
git add .
git commit -m'First commit'
```
1. On change le répertoire courant dans notre projet. 
2. On initialise le dépôt avec `git init`
3. `git add` dit à git d'ajouter tous les fichiers dans le répertoire courant, y compris ceux qui sont dans des sous-répertoires (avec le `.` après la commande).
4. Puis, on **commit** avec un message.

Mais, nous avons promis du détail, donc revenons à notre projet initial qui est simplement un dépôt de code git vide et tentons de comprendre plus en profondeur ce qui s'est passé. Donc si vous êtes parti ailleurs revenons à:

```console
cd ~/projects/my_first_git_project
```

#### Suivre les modifications d'un fichier `git add`

Nous allons maintenant créer un premier fichier. Vous pouvez utiliser votre éditeur de texte favori. Ici, je ne vais même pas utiliser un éditeur et directement créer le fichier et son contenu en utilisant la commande `echo` qui sert à afficher du texte que je vais rediriger (en utilisant `>`) vers un fichier que l'on va nommer `readme.md`.

```console
echo "# Mon premier projet Git" > readme.md
```

> :information_source:
> Le fichier que nous venons de créer est un fichier texte dans un format appelé _Markdown_. Le "#" à son début indique que cette ligne est un titre. Vous pouvez en apprendre plus sur https://openclassrooms.com/fr/courses/1304236-redigez-en-markdown. C'est une très bonne pratique de toujours créer un fichier nommé `readme.md` à la racine de son dépôt de code Git qui va décrire le contenu du dépôt. On va y revenir.

On va tout de suite apprendre une deuxième commande Git. Elle non plus n'a pas besoin d'argument (mais elle peut en prendre, bien entendu) :

```console
git status
```
qui va répondre :

```console
On branch master

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)

	readme.md

nothing added to commit but untracked files present (use "git add" to track)
```

`git status`, commande fort utile, nous permet à tout moment de savoir, comme son nome l'indique, quel est le statut de notre travail avec Git. Avec le temps, nous allons apprendre à comprendre ses retours mais pour le moment attardons nous sur la fin du message :

```console 
nothing added to commit but untracked files present (use "git add" to track)

Untracked files:
  (use "git add <file>..." to include in what will be committed)

	readme.md
```

Git est donc déjà au courant que l'on a créé un fichier. Mais il nous dit "dans votre répertoire de travail, il y a un fichier que je ne connais pas vraiment. Si vous voulez que j'en suive l'évolution, il faut me le dire". Dans sa grande gentillesse il nous indique même le chemin à suivre : `git add <file>..`. Retenez en Anglais: **Tracked** (suivi) et  **Untracked**  (non-suivi).

Faisons ce qu'il nous dit. On va expliquer juste après.

```console
git add readme.md
```

S'il y a pas d'erreur Git, ne va rien nous dire. Mais il a bien fait quelque chose.

#### Le répertoire de travail 

Cette command ne sauvegarde pas encore le fichier. Elle dit simplement à Git "à partir de maintenant, tu dois suivre ce fichier et ses modifications, puis enregistrer son état actuel quelque part pour que je puisse sauvegarder cet état". Plus tard, quand on aura fait notre premier `commit`, c'est cet état qui va être pris en compte.

Retenez en Anglais: **Staging** c'est l'action de préparer quelque chose pour sa prochaine étape. Dans notre cas ajouter un fichier à l'index prépare le commit. Le terme vient de la logistique, en Français ont dirait "aire/point de rassemblement" ou "zone de transit", là où les troupes se préparent, ou la partie de l'entrepôt où on met des paquets avant leur acheminement. En Anglais on va aussi souvent l'utiliser comme un verbe pour préparer un fichier pour être sauvegardé on dit "to stage a file" qui est équivalent à "to add a file to the index".

> :information_source:
> Nous pouvons donc imaginer le travail avec Git comme passer nos fichiers enter trois zones:
> 1. La zone de travail, notre répertoire courant, le répertoire de travail : son contenu est ce que l'on voit dans le navigateur de fichiers. C'est là ou nous modifions nos fichiers.
> 2. la zone de transit - l'index autrement appelé **staging**, les fichiers tels qu'ils sont préparés pour être sauvegardés, enregistrés dans une version (ou révision) spécifique. On a là des "instantanés" des nos fichiers.
> 3. La zone de commit - le travail validé, là où les choses sont enregistrées pour la postérité - des choses que l'on peut aussi donc partager avec d'autres envoyer vers d'autres.

#### Regarder à l'intérieur de `.git`

Mais comprenons d'abord ce qui s'est passé plus en détail. On va jeter un coup d'œil dans les entrailles du monstre. Ce que l'on va voir n'est pas nécessaire pour l'utilisation courante de Git, mais taper des commandes sans comprendre ce qu'elles font va assez rapidement vous faire bloquer. Donc, un peu de souffrance maintenant pour beaucoup de gloire plus loin. Qu'est-ce-qu'on trouve dans le répertoire `.git` ?

Tapons joyeusement une jolie commande:

```console
tree -C .git
```

> :information_source:
> La commande `tree` est un peu comme `ls` mais elle nous montre la structure des répertoires et des fichiers qu'il contiennent, nous avons ajouté l'option `-C` pour que le rendu soit colorié, nous montrant la différence entre fichiers et répertoires. Elle pourrait ne pas être installée sur votre système ; un `ls -lRa` (on reconnait ici le `ls -la`, le `R` est pour Récursif) peut suffire.

```console
.git
├── HEAD
├── config
├── description
├── hooks
│   ├── applypatch-msg.sample
│   ├── commit-msg.sample
│   ├── fsmonitor-watchman.sample
│   ├── post-update.sample
│   ├── pre-applypatch.sample
│   ├── pre-commit.sample
│   ├── pre-push.sample
│   ├── pre-rebase.sample
│   ├── pre-receive.sample
│   ├── prepare-commit-msg.sample
│   └── update.sample
├── index
├── info
│   └── exclude
├── objects
│   ├── a7
│   │   └── 8ab042d5f3b0a2369d27d60368fb2a2eada826
│   ├── info
│   └── pack
└── refs
    ├── heads
    └── tags
```

Nous allons pour le moment ignorer le reste et nous attarder uniquement sur une partie:

```console
.git
├── index
├── objects
│   ├── a7
│   │   └── 8ab042d5f3b0a2369d27d60368fb2a2eada826
```

On a ici un fichier, très important, `index`. Et une structure de répertoires de la forme: `objects/<deux lettres>/<nom-de-fichier-de-38-lettres>`. Ne vous en faites pas si votre objet n'a pas exactement le même nom, c'est normal !
    
L'**index** est la base de données de Git. Elle lui dit pour chaque fichier qu'on l'on veut suivre (**Track**) où il en est dans la vie. 

Dans **objects** est stocké le contenu réel des nos fichiers de la zone de travail qui auront été ajouté à l'index ou enregistré avec un `commit`. Notre "readme.md" a été mis dans une forme compressée dans `objects/a7/8ab042d5f3b0a2369d27d60368fb2a2eada826`. 

> :information_source:
> Ce nom de fichier, bizarre, n'est pas aléatoire, c'est un **SHA**. Git a utilisé ce que l'on nomme "une fonction de hachage" basée sur le contenu du fichier. En gros une fonction de hachage nous permet de prendre un contenu, peu importe sa taille, et de produire en sortie un chaîne de caractères de taille fixe (dans notre cas 40 caractères. Ici les deux premiers caractères sont utilisés pour le nom du répertoire et 38 pour le nom du fichier).
> Changer un seul caractère dans le contenu change complètement la chaîne générée. On parle alors d'un "adressage par le contenu". Quand le contenu change, le nom de fichier (d'ou "adresse") change. 
> La fonction de hachage utilisée s'appelle **SHA-1**. Et partout dans Git, ou presque, nos identifiants vont prendre cette forme. On va parler de **commit**, de **commit-id** de **tree** et de **tree-id**, des **blob**s et tous cela, que l'on vous expliquera plus tard, vont toujours prendre une forme comme ça: `a78ab042d5f3b0a2369d27d60368fb2a2eada826`. Pour rendre la chose un tout petit peu plus lisible le plus souvent on ne va pas utiliser le 40 caractères mais uniquement les 7 premiers. Ainsi pour parler de `a78ab042d5f3b0a2369d27d60368fb2a2eada826` on va parler plutôt de `a78ab04`, mais ça identifie la même chose.

Chaque fichier dans notre répertoire de travail peut avoir trois "hashes" dans l'**index**:

* Un pour son contenu tel qu'il est actuellement dans le répertoire de travail,
* un tel qu'il a été  quand il a été ajouté à l'index
* et un tel qu'il est sauvegardé, pour du vrai, dans notre dépôt.

> :warning:
> Beaucoup de malentendus sur Git viennent de la mécompréhension de cette relation entre le **staging** ou le fait de préparer notre **commit**, notre sauvegarde d'étape, et le **commit** lui-même. C'est pour cela que nous nous y attardons. Donc prenez le temps de comprendre.

Nous sommes prêts ! Enfin. Nous avons créé un fichier et nous l'avons ajouté à l'index. 

Si nous lançons `git status` à nouveau, il nous dira:
```
On branch master

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)

	new file:   readme.md
```

ça y est, Git est prêt pour nous.

#### Sauvegarder un point d'étape `git commit`

Dans le terminal tapons:

```console
git commit -m"Added readme.md"
```

Normalement Git nous répondra avec: 

```console 
[master (root-commit) ec997c4] Added readme.md
 1 file changed, 1 insertion(+)
 create mode 100644 readme.md
```

Voilà. C'est fait! Nous avons sauvegardé un point d'étape. Vous pouvez taper `git status` 

Notre **commit**. A tout jamais à partir de maintenant dans la vie de notre projet nous pourrons revenir dans le passé, savoir quel était le contenu du fichier à ce moment, et nous saurons aussi qui a fait quel changement et **pourquoi**.

> :information_source:
> Nous avons vu, quand nous avons tapé la commande `git add` il a crée le fichier dans une forme comprimée dans son répertoire ./objects/ et il lui a donnée un nom basé sur le contenu. Donc on a perdu le nom de fichier! N'ayez pas peur. Dans ./objects on a deux autres types de fichiers qui vont nous permettre de retrouver notre nom de fichier: `tree` et `commit`. 
Analysons juste un peu ce que l'on a fait ... et puis, rentrons dans le détail de ce que Git, lui, a fait. En effet la commande `commit` comme la commande `add` change non-seulement l'index mais aussi créer des nouveaux objets dans  `.git/objects` 

Donc `git commit` c'est la commande qui sauvegarde, et là on voit une première fois une qui a un argument obligatoire: le `-m`. Cet argument indique le **message de commit**: l'intention de notre changement. C'est incroyablement utile quand on travail seul ("mais pourquoi grands-dieux ai-je fait cela ! ah .. oui..") mais c'est encore plus important quand on travail avec d'autres. En tout état de cause Git refusera de sauvegarder quoi que ce soit si vous n'ajoutez pas de message.

> :warning:
> En tant que quelqu'un qui recrute pas mal de développeurs sachez, que quand je regarde du code des candidats, je regarde les messages de commit autant que je regarde le code lui-même. 

#### Sauvegarder un deuxième changement puis un troisième

On est sur une lancée donc continuons ! Faisons un deuxième changement. Ouvrez notre "readme.md" avec votre éditeur de text préféré et ajoutons par exemple:

```markdown
# Mon premier projet Git

Nous avons appris aujourd'hui les commandes Git suivantes:

1. `git init` - initialiser un nouveau dépôt git
2. `git status` - connaître l'état du répertoire de travail par rapport au dépôt git
3. `git add` - ajouter des fichiers à l'index git pour préparer un commit
4. `git commit -m"{message de commit}"` - sauvegarder un point d'étape dans le dépôt git
```

Après avoir sauvegardé le fichier, si nous tapons `git status`à nouveau nous aurons un message un peu différent.

```console
On branch master
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git checkout -- <file>..." to discard changes in working directory)

	modified:   readme.md

no changes added to commit (use "git add" and/or "git commit -a")
```

Super. Git est au courant que le fichier a été modifié .. et il nous donne même des indications sur l'étape suivante. On y va!

De nouveau: 
 
```console
git add readme.md
```

Puis:

```console
git commit -m"Add the list of commands we learned today."
```

Qui nous répond par:

```console
[master 745866a] Add the list of commands we learned today.
 1 file changed, 8 insertions(+), 1 deletion(-)
 rewrite readme.md (100%)
 ```

> :information_source:
> Astuce 1: si cela vous fatigue de taper chaque fois `add` puis `commit` on a un raccourci : `git commit -am"mon message commit"` l'option `-a` ajoutée ici, dit **all** ... Git va ajouter au commit tous les fichiers suivi dans l'index qui auront été modifié. Par contre si un fichier n'a pas encore été ajouté une première fois il est **Untracked** il va rien faire pour celui-là.
> Astuce 2: si vous avez plein de fichiers dans le répertoire et vous n'avez pas envie de les ajouter un par un, vous pouvez les ajouter tous d'un coup avec `git add .` mais attention, souvent on a des fichiers qui traînent et que l'on ne veut pas forcement dans son dépôt. On verra ça plus tard.

Pour l'exercice créons maintenant un deuxième fichier. Mettons dans notre dépôt un fichier de licence qui va expliquer aux gens qui pourront y avoir accès ce qu'ils peuvent faire, et ce qu'ils ne peuvent pas faire avec; 

```console
echo "Git Example by OpenClassRooms\n\nTo the extent possible under law, the person who associated CC0 with\nGit Example  has waived all copyright and related or neighboring rights\nto Git Example.\n\nYou should have received a copy of the CC0 legalcode along with this\nwork.  If not, see <http://creativecommons.org/publicdomain/zero/1.0/>." > LICENSE
```

#### Récapitulatif `git init`,  `git add` et `git commit`

* `git init` - créer un nouveau dépôt Git, vide.
* `git add` - ajouter un fichier de notre zone de travail à l'index
* `git commit` - valider et sauvegarder les fichiers tels qu'ils ont été ajouté à l'index
* `git status` - pour voir où on en est.. le fichier a-t-il été ajouté à l'index ?  A-t-il été modifié depuis qu'il a été validé ?


Nous sommes maintenant les heureux propriétaires d'un dépôt Git avec deux fichiers, et trois **commits**. Voyons comment cela se présente, à l'intérieur de Git. Au chapitre suivant!
