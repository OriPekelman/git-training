### Au coeur du dépôt, au coeur du commit

Le **commit** est l'objet le plus intéressant de Git, notre outil principal pour construire une historique de notre code, de nommer des versions, de collaborer avec d'autres. 

Chaque fois que nous tapons la commande `git commit` nous créons un nouvel enregistrement, un nouveau point d'étape.

#### Mais, au juste, c'est quoi précisément un **commit** ?

Pour bien comprendre le **commit** nous devons faire un petit détour et rencontrer deux autres concepts. Le **blob** qui est le contenu de nos fichiers et les **tree** qui sont les arborescences successives de fichiers.  

Pour comprendre entamons un nouveau voyage dans les entrailles de la bête. Où en est le contenu de notre répertoire caché le `.git`. 

```console
tree -C .git
```

En réalité dans **objects** Git va mettre _toutes_  les choses qu'il va gérer:
d'abord notre "readme.md" compressé (maintenant on a même deux versions de celui-ci) ainsi que notre "LICENSE" ce type d'objet sont appelés **blob** (en Anglais Binary Large Object). 

##### Blobs

Un "**blob**" ça peut représenter un fichier code source, une image, toute chose. Comme on a fait un changement sur "readme.md" il va être représenté deux fois. Une pour chaque version. 

> :information_source: 
> Comme nous avons dit les noms de fichiers sont maintenant quelque chose qui représente son contenu. Si on a 10 fichiers qui ont les même contenu, Git, va les enregistrer une seule fois sous un seul nom. Pour mieux lire nos **sha**s, souvent, au lieu de référencer les 40 caractères on va prendre le 7 premiers. Ca nous suffit pour bien les identifier.. et ça reste unique dans presque tous les cas. Donc au lieu de parler de `521ae64678d4504b7556fee27c7e84f8181f3794` on va le plus souvent parler de `521ae64`.

Donc le nom de fichier ... il est parti où?

#### **Tree**s et **Commit**s

Dans le même répertoire Git un autres type d'objet:

* Objets de type **tree** - ceux ci vont contenir nos noms de fichiers, et référencer les objets de type **blob** qui vont avoir le contenu de ces fichiers, ainsi que les droits qui y sont attachés.

Maintenant les noms de fichiers de tous ces objets sous `.git/objects` se ressemblent (ces sont tous des choses dont le nom de fichier est un "hash"). Just en regardant cette liste de fichiers on ne peut pas les distinguer, mais à l'intérieur les **commits**, les **tree*s et les **blob**s ont des formats différents.


##### Voir les objets avec **git show**

`git show` est une commande très pratique, on lui donne un objet git de tout type et elle montre le contenu. Utilisons la pour découvrir les arbres. On peut l'utiliser pour voir nos **blob**s, mais aussi. nos **commit**s et nos **tree**s.

##### A l'intérieur du **tree** - notre arborescence 

L'objet appelé **7e815cf** en est une arborescence, un "**tree**":

```console
git show 563449f
```

Le résultat de la commande est très simple:

```
tree 563449f

LICENSE
readme.md
```

Voilà **563449f** est tout simplement une liste de fichiers. On en a deux ici. Mais nous avons pris l'habitude de creuser un peu plus... donc nous allons utiliser une commande de plus bas niveau qui nous donnera bien plus de détails `git ls-tree`:

```console
git ls-tree 563449f
```

Et voilà pour notre résultat bien plus détaillé:

```console
100644 blob 521ae64678d4504b7556fee27c7e84f8181f3794	LICENSE
100644 blob 3fbc9028810ecb8fd97a67c5d0315b7bd11b633a	readme.md
``` 

Le vrai contenu du **tree** n'a pas uniquement les noms de fichiers mais quatre champs:

```
{filemode} {type} {sha}	{filename}
```

* **filemode** - ce sont les métadonnées sur le fichier tels qu'ils sont le système de fichier. Ici par exemple, *10644* représente un fichier régulier non-exécutable. Si on avait *100755* cela aurait été un fichier avec droits d'éxécution pour son propriétaire, *120000* eut été un lien symbolique (Si ces termes ne sont pas familiers pour vous pouvez jeter un coup d'oeil sur https://openclassrooms.com/fr/courses/1088326-les-chmod) mais, passons, cela n'est pas très important pour l'instant.
* **type** peut être soit **blob** soit **tree**. Donc soit un fichier, soit un sous-répertoire.
* **sha** - -vous l'auriez deviné est le "hash" ou le nom de fichier de quelque chose qui va apparaître dans notre `.git/objects`
* **filename**, finalement, est notre nom de fichier (ou de répertoire)

Voilà, on voit comment tout se remet en place... avec nos **blob**s et nos **tree**s nous pouvons recréer des arborescences avec les bons noms de fichiers, rangés là où ils sont censés être et avec un contenu bien spécifique. 

> :information_source:
> Le lecteur astucieux aura remarqué pour qu'on a perdu quelque chose à laquelle on est habitués: la date de création et de modification de ces fichiers. Nous retrouvons des dates on niveaux des **commits**

#####  Les sous-répertoires

Donc chaque *tree* nous permet de reconstruire un état d'un répertoire avec des fichiers qui ont un contenu connu. Essayons maintenant de créer un sous-répertoire, nous avons déjà rencontré la commande `mkdir`:

```console
mkdir files
```
et puis notre vieil ami qui nous montre l'état de notre zone de travail:

```console
git status
```

> :warning: 
> Quoi ? Rien ? Quelle trahison ?! nous avons crée un nouveau répertoire mais git ne nous dit rien. En effet Git ne sait pas traquer des répertoires vides. Ce normal quand on y pense. Dans Git un *tree* ce quelque chose qui représente une liste de fichiers chacun avec un contenu particulier, s'il y a pas de contenu vers quoi va t-il pointer ?

######  Les sous-répertoires vides
L'usage pour garder des répertoires vides est de créer un petit fichier vide qu'on nomme `.gitkeep` puis de le "commiter", le valider.

```console
touch files/.gitkeep
git add files/.gitkeep
git commit -m'Add .gitkeep so files will be added to the repository'
```
Dans notre `.git/objects` on va donc avoir 4 nouveaux fichiers qui vont apparaître.

Un object pour le **commit** (nous verrons ça juste après...), un nouveau **tree** qui représente notre racine qui a changé.

```console
git ls-tree ea2abd3

100644 blob 521ae64678d4504b7556fee27c7e84f8181f3794	LICENSE
040000 tree d564d0bc3dd917926892c55e3706cc116d5b165e	files
100644 blob 3fbc9028810ecb8fd97a67c5d0315b7bd11b633a	readme.md
``` 

Un deuxième **tree** (monsieur *d564d0*) qui va simplement contenir :

``` 
git ls-tree d564d0

100644 blob e69de29bb2d1d6434b8b29ae775ad8c2e48c5391	.gitkeep
```

Puis l'ami *e69de29* qui est notre fichier vide nommé `.gitkeep`.

> :information_source:
> Nous vous avons raconté que c'est le contenu du fichier qui va déterminer le nom du fichier, et rien d'autre. Et là on a un fichier vide. Faites l'exercice.. https://www.google.com/search?q="e69de29bb2d1d6434b8b29ae775ad8c2e48c5391" vous allez en trouver. Plein de fichiers différents. complètement vides avec des noms différents.

Résumons: 

Si nous suivons le premier **tree-id** que nous avons vu **563449f** cela nous donnera:
```
.
├── LICENSE
└── readme.md
```
Mais suivre le deuxième *tree*, le **ea2abd3** nous amènera à:

```
├── LICENSE
├── files
│   └── .gitkeep
└── readme.md
```

##### Boucler la boucle avec le **commit**

Le dernier type d'objet que l'on va trouver dans `.git/objects/` ce sont les **commit**s.

Objets de type **commit** - ça, c'est  un élément central! le **commit** est cette trace de nos changements. Un commit principalement identifie un **tree** particulier et un (ou d'ailleurs plusieurs) **commit**s parents.

Le commit nous permet de construire les relations entre les **tree**s, enregistrer les changements. 

Pour rappel, dans ce cour nous avons utilisé déjà la commande `git commit` quatre fois:

1. Quand nous avons ajouté `readme.md` (__commit 5e8354a6__)
2. Quand nous avons modifié `readme.md` pour ajouter la liste de command qu'on a appris (__commit 208de9d__)
3. Quand on a ajouté `LICENSE`  (__commit d673dbcd__)
4. puis quand nous avons ajouté `files/.gitkeep` (__commit 06ab718f__)

Nous allons étudier le deuxième, **f72b3fd**, son contenu ressemble à ceci:

```
tree 5c775290031a9583224f0c9294beac29e47b18a2
parent 5b8cb4111e2dc88c333d20e9a3fca38cdbe7d312
author Ori Pekelman <ori@platform.sh> 1539235050 +0100
committer Ori Pekelman <ori@platform.sh> 1545050636 +0100

Adding a license file
```

Donc la structure est:

* tree {tree_sha} c'est la référence, le **sha**, le **tree-id** qui représente notre arborescence
* parent {parents} c'est le commit parent, on y reviendra
* author {author_name} <{author_email}> {author_date_seconds}  {author_date_timezone} c'est l'auteur du code avec son nom et son email et un **timestamp**,  le moment dans lequel le code aura été crée
* committer {committer_name} <{committer_email}> {committer_date_seconds} {committer_date_timezone} c'est la personne qui commit le code, qui n'est pas toujours l'auteur... puis le moment où le commit a été fait ( Notons que d'habitude **author** et **committer**  sont la même personne)
* {commit message} - le message, celui qu'on a ajouté avec le drapeau `-m'...'` qui contient le "pourquoi" du changement.

Donc on a bien compris: le commit c'est une référence vers un **tree-id** (et lui on a déjà vu nous permet de reconstituer un espace de travail... une arborescence  avec des fichiers avec un contenu spécifique) cette référence contient quelques informations supplémentaires : qui a fait le changements, quand, pourquoi ... et ... le "commit parent". Le commit parent c'est donc l'état précédent de notre arborescence. Donc chaque **commit** peut aussi être appelé une "révision". Quand on va, plus tard, voir la liste des **commits** on verra la liste des toutes les révisions apportées à notre dépôt.

Mais d'habitude nous allons jamais regardé les structures internes de Git mais utiliser des commandes qui, en plus nous donnent davatange d'informations. Regardons donc le deuxième **commit** avec la command `git show` : 

```console
git show 208de9d

commit 208de9d431298ca3f2f3e0523ec6e0ff98538e55
Author: Ori Pekelman <ori@platform.sh>
Date:   Thu Oct 11 06:10:30 2018 +0100

    Add the list of commands we learned today.

diff --git a/readme.md b/readme.md
index 6c83bba..3fbc902 100644
--- a/readme.md
+++ b/readme.md
@@ -1 +1,9 @@
 # Mon premier projet Git
+
+Nous avons appris aujourd'hui les commandes Git suivantes:
+
+1. `git init` - initialiser un nouveau dépôt git
+2. `git status` - connaître l'état du répeetoire de travail par rapport au dépôt git
+3. `git add` - ajouter des fichiers à l'index git pour préparer un commit
+4. `git commit -m"{message de commit}"` - sauvegarder un point d'étape dans le dépôt git
+
 ```

Donc là nous ne voyons plus les **tree** qui est en gros un détail interne mais uniquement les informations qui ont trait avec notre changement, voyons ligne par ligne:

1. commit - l'identifiant du commit, son **sha**, le **commit-id**
2. Author:  - qui a fait le changement
3. Date: - quand est-ce que le changement a été fait
4. Le message du commit
5. Le diff. La différence entre le fichier readme.md quand il avait le **sha** `6c83bba` puis quand il a le sha `3fbc902`.

Si le **tree** nous a beaucoup servi pour comprendre la structure interne de Git, il s'agit bien d'une chose interne. Dans notre travail de tous les jours c'est presque exclusivement avec les **commits** qu'on va interagir. 

> :information_source: Git ne sauvegarde pas les différences entre le deux fichiers, mais réellement le contenu de chacune de versions, à part. Cette différence, cet **diff** que nous voyons est calculé dynamiquement quand nous utilisons la commande `git show`.

> :information_source:
> Nous avons  un tout petit peu simplifié l'histoire, si vous regardez un vrai dépôt Git avec plein de fichiers et plein de **commits** vous ne verrez pas un objet pour chaque fichier. En effet Git va de temps en temps faire du nettoyage et compresser un peu plus loin (le mot clé est **pack**). Mais ceci en dehors du cadre du présent cours.

#### Récapitulatif **blob**, **commit** et **tree**

* **blob** - le blob est un fichier de la zone de travail qui a été ajouté à l'index - il contient le vrai contenu du fichier dans une forme compressée, son nom composé de 40 caractères (**SHA**) qui est une signature de son contenu.
* **tree** - contient la liste des fichiers (donc des identifiants des blobs de 40 caractères)... avec leurs noms et leurs droits.  On peut aussi dans la liste se référer à un autre **tree** par son **tree-id** ce qui va nous donner un sous-répertoire.
* **commit** - est l'enregistrement d'un état, la validation, à partir d'un **commit** nous pouvons reconstruire notre zone de travail avec un **tree** spécifique. Il contient des informations sur l'auteur du changement et sa raison. Il peut se référer à un parent.
