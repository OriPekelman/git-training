#### Au juste c'est quoi un **commit** ?

Wow! plein de choses. On n'a ajouté que deux fichiers, et pour autant il y'en a 9 dans le sous-répertoire **objets** . Intéressant! Etudions.

En réalité dans **objects** Git va mettre _tous_ les objets qu'il va gérer.

Donc d'abord notre "readme.md" compressé (maintenant on a deux versions de celui-ci) et notre "LICENSE" ce type d'objet sont appelés **blob** (en Anglais Binary Large Object). Ca peut représenter un fichier code source, une image, toute chose. Comme on a fait un changement sur "readme.md" il va être représenté deux fois. Une pour chaque version. Mais comme nous avons dit le nom de fichier est maintenant quelque chose qui représente son contenu.. l'objet lui-même est "anonyme". Si on a 10 fichiers qui ont les même contenu, Git, va les enregistrer une seule fois. Donc le nom de fichier ... il est où?

Donc il va y aussi dans le même répertoire mettre deux types d'objets internes:

* Objets de type **tree** - ceux ci vont contenir nos noms de fichiers, et référencer les objets de type **blob** qui vont avoir le contenu de ces fichiers, ainsi que les droits qui y sont attachés.
* Objets de type **commit** - ça, c'est  un élément central! le **commit** est cette trace de nos changements.

Maintenant tous ces objets sous `.git/objects` se ressemblent (ces sont tous des choses dont le nom de fichier est un "hash"). Mais à l'intérieur les **commits**, les **tree*s et les **blob**s ont des formats différents.


Découvrons d'abord le **tree**, si nous prenons **7e815cf** (pour mieux lire nos **shas**, souvent, au lieu de référencer les 40 caractères on va prendre le 7 premiers. Ca nous suffit pour bien les identifier.. et ça reste unique dans presque tous les cas), voilà à quoi va ressembler son contenu :

```console
git ls-tree 7e815cf
```

```console
100644 blob 521ae64678d4504b7556fee27c7e84f8181f3794	LICENSE
100644 blob 134b99a9a6e48059f4867cb9cb731f04b54ed054	readme.md

Donc quatre champs:
```
{filemode} {type} {sha}	{filename}
```

* **filemode** - ce sont les métadonnées sur le fichier tels qu'ils sont le système de fichier. Ici par exemple, *10644* répresente un fichier régulier non-exécutable. Si on avait *100755* cela aurait été un fichier avec droits d'éxécution pour son propriétaire, *120000* eut été un lien symbolique (Si ces termes ne sont pas familiers pour vous pouvez jéter un coup d'oeil sur https://openclassrooms.com/fr/courses/1088326-les-chmod) mais, passons, cela n'est pas très important pour l'instant.
* **type** peut être soit **blob** soit **tree**. Donc soit un fichier, soit un sous-répertoire.
* **sha** - -vous l'auriez deviné est le "hash" ou le nom de fichier de quelque chose qui va apparaître dans notre `.git/objects`
** **filename** finalement est notre nom de fichier (ou de répertoire)

Voilà, on voit comment tout se remet en place... avec nos **blob**s et nos **tree**s nous pouvons recréer des des arboresences avec les bons noms de fichiers rangés là où ils sont censés être. 

> :info:
> Le lecteur astucieux aura remarqué pour qu'on a perdu quelque chose à laquelle on est habitués: la date de création et de modification de ces fichiers. Nous retrouvons des dates on niveaux des **commits**

Donc chaque *tree* nous permet de reconstruire un état d'un répertoire. Essayons maintenant de créer un sous-répertoire, nous avons déjà rencontré la commande `mkdir`:
```
mkdir files
```
et puis notre vieil ami qui nous montre l'état de notre zone de travail:
```
git status
```

Quoi ? Rien ? Quelle trahison ?! nous avons crée un nouveau répertoire mais git ne nous dit rien. En effet Git ne sait pas traquer des répertoires vides. Ce normal quand on y pense. Dans Git un *tree* ce quelque chose qui représente une liste de fichiers chacun avec un contenu particulier, s'il y a pas de contenu vers quoi va t-il pointer ?

L'usage pour garder des répertoires vides est de créer un petit fichier vide qu'on nomme `.gitkeep` puis de le "commiter".

```
touch files/.gitkeep
git add files/.gitkeep
git commit -m'add .gitkeep so files will be added to the repository'
```
Dans notre `.git/objects` on va donc avoir 4 nouveaux fichiers qui vont apparaître.

Un object pour le **commit** (nous verrons ça juste après...), un nouveau **tree** qui représente notre racine qui a changé.

``` 
100644 blob 521ae64678d4504b7556fee27c7e84f8181f3794	LICENSE
040000 tree c3dd917926892c55e3706cc116d5b165e	files
100644 blob 134b99a9a6e48059f4867cb9cb731f04b54ed054	readme.md
``` 

Un deuxième **tree** (monsieur *c3dd917*) qui va simplement contenir :
``` 
100644 blob e69de29bb2d1d6434b8b29ae775ad8c2e48c5391	.gitkeep
```
Puis l'ami *e69de29bb2d1d6434b8b29ae775ad8c2e48c5391* qui est notre fichier vide nommé `.gitkeep`.

> :info:
> Nous vous avons raconté que c'est le contenu du fichier qui va déterminer le nom du fichier, et rien d'autre. Et là on a un fichier vide. Faites l'exercice.. https://www.google.com/search?q="e69de29bb2d1d6434b8b29ae775ad8c2e48c5391" vous allez en trouver. Plein de fichiers différents. complètement vides avec des noms différents.

Résumons: 

Si nous suivons le premier **tree-id** que nous avons vu **7e815cf** cela nous donnera:
```
.
├── LICENSE
└── readme.md
```
Mais suivre le deuxième *tree* le **c3dd917** nous donnera:

```
├── LICENSE
├── files
│   └── .gitkeep
└── readme.md

```

Le SHA de `LICENSE` n'aura pas changé ni celui de `readme.md` donc dans le deux cas c'est précisément le même contenu. Ce qui nous amène à la découverte de ce dernier élément du puzzle. Le **commit**. Le commit nous permet de construire les relations entre les Trees, enregistrer les changements. Regardons un de nos commits.

**commit 02c45d5**

```
tree 7e815cf parent fa63765 author Ori Pekelman <ori@***> 1539869399 +0200 committer Ori Pekelman <ori@***> 1539869399 +0200 Adding a license file
```

Donc qu'il y a t-il ici ?  Regardons la structure:
``` 
tree {tree_sha}
{parents}
author {author_name} <{author_email}> {author_date_seconds} {author_date_timezone}
committer {committer_name} <{committer_email}> {committer_date_seconds} {committer_date_timezone}

{commit message}
```

* **tree** est la référence, le **sha**, le **tree-id** qui représente notre arborescence
* **parent** c'est le commit parent, on y reviendra
* **author** c'est l'auteur du code avec son nom et son email **author_date_seconds** un timestamp c'est le moment dans lequel le code aura été crée
* **comitter**, avec son nom et son email -  politesse oblige, c'est la personne qui commit le code, qui n'est pas toujours l'auteur... puis **committer_date_seconds** le moment où le commit a été fait. Notons que d'habitude **author** et **committer**  sont la même personne
* **commit message** le message, celui qu'on a ajouté avec le drapeau `-m'...'` qui contient le "pourquoi" du changement.

Donc on a bien compris: le commit c'est une référence vers un **tree-id** (et lui on a déjà vu nous permet de reconstituer un espace de travail... une arborescence  avec des fichiers avec un contenu spécifique) cette référence contient quelques informations supplémentaires : qui a fait le changements, quand, pourquoi ... et ... le "commit parent". Le commit parent c'est donc l'état précédent de notre arborescence. Donc chaque **commit** peut aussi être appelé une "révision". Quand on va, plus tard, voir la liste des **commits** on verra la liste des toutes les révisions apportées à notre dépôt.

> :info:
> Nous avons  un tout petit peu simplifié l'histoire, si vous regardez un vrai dépôt Git avec plein de fichiers et plein de **commits** vous ne verrez pas un objet pour chaque fichier. En effet Git va de temps en temps faire du nettoyage et compresser un peu plus loin (le mot clé est **pack**). Mais ceci en dehors du cadre du présent cours.

#### Récapitulatif **blob**, **commit** et **tree**

* **blob** - le blob est un fichier de la zone de travail qui a été ajouté à l'index - il contient le vrai contenu du fichier dans une forme compressée, son nom composé de 40 caractères (**SHA**) qui est une signature de son contenu.
* **tree** - contient la liste des fichiers (donc des identifiants des blobs de 40 caractères)... avec leurs noms et leurs droits.  On peut aussi dans la liste se référer à un autre **tree** par son **tree-id** ce qui va nous donner un sous-répertoire.
* **commit** - est l'enregistrement d'un état, la validation, à partir d'un **commit** nous pouvons reconstruire notre zone de travail avec un **tree** spécifique. Il contient des informations sur l'auteur du changement et sa raison. Il peut se référer à un parent.


Toute la magie de git va se déployer à partir de ce concept simple de **commit**. Git va nous permettre de faire nos modifications, chaque fois, nous allons enregistrer des états. Puis il va nous permettre de sauter de l'un à l'autre. De comparer deux états .. même d'en faire des mélanges.
