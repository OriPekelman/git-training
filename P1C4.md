###  Sauvegardons notre travail!

#### Suivre les modifications d'un fichier `git add`

Nous allons maintenant créer un premier fichier. Vous pouvez utiliser votre éditeur de texte favori. Dans ce cas je ne vais même pas utiliser un éditeur et directement créer le fichier et son contenu en utilisant la commande `echo` qui sert pour afficher du texte que je vais rédiriger (en utilisant `>`) vers un fichier que l'on va nommer `readme.md`.

```console
echo "# Mon premier projet Git" > readme.md
```

> :info:
> Le fichier que nous venons de créer est un fichier texte dans un format appelé _Markdown_. Le "#" à son début indique que cette ligne est un titre. Vous pouvez en apprendre plus sur https://openclassrooms.com/fr/courses/1304236-redigez-en-markdown C'est une très bonne pratique de toujours créer un fichier nommé "readme.md" à la racine de son dépôt de code Git qui va décrire le contenu du dépôt. On va y revenir.

On va toute-de-suite apprendre une deuxième commande Git. Elle aussi n'a pas besoin d'arguments:

```console
git status
```
qui va répondre par:

```console
On branch master

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)

	readme.md

nothing added to commit but untracked files present (use "git add" to track)
```

`git status`, commande forte utile, nous permet à tout moment de savoir, comme son nome l'indique, quel est le statut de notre travail avec Git. Avec le temps nous allons apprendre à comprendre ses retours mais pour le moment attardons nous sur la fin du message :

```console 
nothing added to commit but untracked files present (use "git add" to track)

Untracked files:
  (use "git add <file>..." to include in what will be committed)

	readme.md
```

#### Le répertoire de travail 

Donc Git est déjà au courant que l'on a crée un fichier. Mais il nous dit "hé dans votre répertoire de travail il y a un fichier que je ne connais par vraiment. Si vous voulez que j'en tienne compte il faut me le dire". Dans sa grande gentillesse il nous indique même le chemin à suivre `git add <file>..`. Retenez en Anglais: **Tracked** (suivi) et  **Untracked**  (non-suivi).

Faisons ce qu'il nous dit. On va expliquer juste après.

```console
git add readme.md
```

S'il y a pas d'erreur Git va rien nous dire. Mais il a bien fait quelque chose.

Cette command ne sauvegarde pas encore le fichier. Elle dit simplement à Git: à partir de maintenant tu dois suivre ce fichier et ses modifications, puis, STP, enregistre son état actuel quelque part pour que je puisse sauvegarder cet état. Plus tard, quand on aura fait notre premier `commit` c'est cet état qui va être pris en compte.

Retenez en Anglais: **Staging** c'est l'action de préparer quelque chose pour sa prochaine étape. Dans notre cas ajouter un fichier à l'index prépare le commit.

#### Regarder à l'intérieur de `.git`

Mais d'abord, comprenons ce qui s'est passe plus en détail. On ba jeter un coup d'oeil dans les entrailles du monstre. Ce que l'on va voir n'est pas nécessaire pour l'utilisation courante de Git. Mais taper des commandes sans comprendre ce qu'elles font va assez rapidement vous faire bloquer. Donc, un peu de souffrance maintenant pour beaucoup de gloire plus loin. Qu'est-ce-qu'il y a dans le répertoire `.git` ?

Tapons joyeusement une jolie commande:

```console
tree -C .git
```

> :info:
> La commande `tree` est un peu comme `ls` mais elle nous montre la structure des répertoires et des fichiers qu'il contiennent, nous avons ajouté l'option `-C` pour que le rendu soit colorié, nous montrant la différence entre fichiers et répertoires.

```console
.git
├── HEAD
├── config
├── description
├── hooks
│   ├── applypatch-msg.sample
│   ├── commit-msg.sample
│   ├── fsmonitor-watchman.sample
│   ├── post-update.sample
│   ├── pre-applypatch.sample
│   ├── pre-commit.sample
│   ├── pre-push.sample
│   ├── pre-rebase.sample
│   ├── pre-receive.sample
│   ├── prepare-commit-msg.sample
│   └── update.sample
├── index
├── info
│   └── exclude
├── objects
│   ├── a7
│   │   └── 8ab042d5f3b0a2369d27d60368fb2a2eada826
```

Nous allons pour le moment ignorer le reste et nous attarder uniquement sur une partie:

```console
.git
├── index
├── objects
│   ├── a7
│   │   └── 8ab042d5f3b0a2369d27d60368fb2a2eada826
```

On a ici un fichier, très important, `index`. Et une structure de répertoires de la forme: `objects/<deux lettres>/<nom-de-fichier-de-38-lettres>`.
    
L'**index** est la base de données de Git. Elle lui dit pour chaque fichier qu'on l'on veut suivre (**Track**) où il en est dans la vie. 

Dans **objects** est stocké le contenu réel des nos fichiers de la zone de travail qui auront été ajouté à l'index ou enregistré avec un `commit`. Notre "readme.md" a été mis dans une forme compressée dans `objects/a7/8ab042d5f3b0a2369d27d60368fb2a2eada826`. 

> :info:
> Ce nom de fichier, bizarre, n'est pas aléatoire. Git a utilisé ce que l'on nomme "une fonction de hachage" basée sur le contenu du fichier. En gros une fonction de hachage nous permet de prendre un contenu, peu importe sa taille, et de produire en sortie un chaîne de caractères de taille fixe (dans notre cas 40 caractères: deux utilisés pour le nom du répertoire et 38 pour le nom du fichier). Changer un seul caractère dans le contenu change complètement la chaîne générée. On parle alors d'un "adressage par le contenu". Quand le contenu change, le nom de fichier (d'ou "adresse") change.

Chaque fichier dans notre répertoire de travail peut avoir trois "haches" dans l'**index**:

* Un pour son contenu tel qu'il est actuellement dans le répertoire de travail,
* un tel qu'il a été  quand il a été ajouté à l'index
* et un tel qu'il est sauvegardé, pour du vrai, dans notre dépôt.

Nous sommes prêts ! finalement. Nous avons crée un fichier, et nous l'avons ajouté à l'index. 

Si nous tapions `git status` à nouveau il nous dira:
```
On branch master

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)

	new file:   readme.md
```

Donc voilà, Git est prêt pour nous.

#### Sauvegarder un point d'étape `git commit`

Dans le terminal tapons:

```console
git commit -m"Added readme.md"
```

Normalement Git nous répondra avec: 

```console 
[master (root-commit) ec997c4] Added readme.md
 1 file changed, 1 insertion(+)
 create mode 100644 readme.md
```

Voilà. C'est fait! Nous avons sauvegardé un point d'étape. Vous pouvez taper `git status` 

Notre **commit**. A tout jamais à partir de maintenant dans la vie de notre projet nous pourrons revenir dans le passé, savoir quel était le contenu du fichier à ce moment, et nous saurons aussi qui a fait quel changement et **pourquoi**.

Analysons juste un peu ce que l'on a fait ... et puis, rentrons dans le détail de ce que Git, lui, a fait.

Donc `git commit` c'est la commande qui sauvegarde, et là on voit une première fois une qui a un argument obligatoire: le `-m`. Cet argument indique le **message de commit**: l'intention de notre changement. C'est incroyablement utile quand on travail seul ("mais pourquoi grands-dieux ai-je fait cela ! ah .. oui..") mais c'est encore plus important quand on travail avec d'autres. En tout état de cause Git refusera de sauvegarder quoi que ce soit si vous n'ajoutez pas de message.

> :warning:
> En tant que quelqu'un qui recrute pas mal de gens sachez, que quand je regarde du code des candidats, je regarde les messages de commit autant que je regarde le code lui-même. 

On est sur une lancée donc continuons ! Faisons un deuxième changement. Ouvrez notre "readme.md" avec votre éditeur de text préféré et ajoutons par exemple:

```markdown
# Mon premier projet Git

Nous avons appris aujourd'hui les commandes Git suivantes:

1. `git init` - initialiser un nouveau dépôt git
2. `git status` - connaître l'état du répeetoire de travail par rapport au dépôt git
3. `git add` - ajouter des fichiers à l'index git pour préparer un commit
4. `git commit -m"{message de commit}"` - sauvegarder un point d'étape dans le dépôt git
```

Après avoir sauvegardé le fichier, si nous tapons `git status`à nouveau nous aurons un message un peu différent.

```console
On branch master
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git checkout -- <file>..." to discard changes in working directory)

	modified:   readme.md

no changes added to commit (use "git add" and/or "git commit -a")
```

Super. Git est au courant que le fichier a été modifié .. et il nous donne même des indications sur l'étape suivante. On y va!

De nouveau: 
 
```console
git add readme.md
```

Puis:

```console
git commit -m"Add the list of commands we learnt today."
```

Qui nous répond par:

```console
[master 745866a] Add the list of commands we learnt today.
 1 file changed, 8 insertions(+), 1 deletion(-)
 rewrite readme.md (100%)
 ```

> :info:
> Astuce: si cela vous fatigue de taper chaque fois `add` puis `commit` on a un raccourci : `git commit -am"mon message commit"` l'option `-a` ajoutée ici, dit **all** ... Git va ajouter au commit tous les fichiers suivi dans l'index qui auront été modifié. Par contre si un fichier n'a pas encore été ajouté une première fois il est **Untracked** il va rien faire pour celui-là.

#### Au juste c'est quoi un **commit** ?


En réalité dans **objects** Git va mettre _tous_ les objets qu'il va gérer.

Donc d'abord notre "readme.md" compressé (maintenant on a deux versions de celui-ci) et notre "LICENSE" ce type d'objet sont appelés **blob** (en Anglais Binary Large Object). Ca peut répresenter un fichier code source, une image, toute chose. Comme on a fait un changement sur "readme.md" il va être représenté deux fois. Une pour chaque version. 

Puis il va aussi dans le même répertoire mettre deux types d'objets internes:

* Objets de type **tree** 
* Objets de type **commit**
