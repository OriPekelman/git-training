### Let's save our work!

We have chosen to do everything very, but very slowly by explaining each step of the way to you. But you were also promised simplicity. So.. let's imagine we have a project, not yet under Git control (let's call it `my_existing_project`) that contains our source code files. How to get them under Git control simply and quickly?

Nothing's easier:
```console
cd ~/projects/openclassrooms/my_existing_project
git init
git add .
git commit -m'First commit'
```
1. We change the current directory in our project.
2. We initialize the repository with `git init`
3. `git add` tells git to add all files in the current directory, including those in subdirectories (with the `.` after the command).
4. Then we **commit** with a message.

But, we promised detail, so let's go back to our original project which is just an empty git code repository and try to understand more in depth what happened. So if you've gone elsewhere let's go back to:

If there is no Git error, won't tell us anything. But he did something right.

#### The working directory

This command does not save the file yet. It just tells Git "from now on, you need to track this file and its changes, then save its current state somewhere so I can save that state." Later, when we have made our first `commit`, it is this state that will be taken into account.

Remember in English: **Staging** is the action of preparing something for its next stage. In our case adding a file to the index prepares the commit. The term comes from logistics, in French we would say "air/gathering point" or "transit zone", where the troops are preparing, or the part of the warehouse where we put packages before their delivery. In English we will also often use it as a verb to prepare a file to be saved, we say "to stage a file" which is equivalent to "to add a file to the index".

> :information_source:
> So we can imagine working with Git as passing our files between three areas:
> 1. The work area, our current directory, the working directory: its content is what we see in the file browser. This is where we edit our files.
> 2. the staging area - the index otherwise known as **staging**, the files as they are prepared to be saved, saved in a specific version (or revision). Here we have "snapshots" of our files.
> 3. The commit area - the committed work, where things are saved for posterity - things that can also be shared with others and sent to others.

#### Look inside `.git`

But let's first understand what happened in more detail. We're gonna take a peek into the monster's innards. What we're about to see isn't necessary for everyday use of Git, but typing commands without understanding what they do will get you stuck fairly quickly. So a little pain now for a lot of glory later. What's in the `.git` directory?

Let's happily type a nice command:

```console
tree -C .git
```

> :information_source:
> The `tree` command is a bit like `ls` but it shows us the structure of the directories and the files they contain, we added the `-C` option so that the rendering is colored, showing us the difference between files and directories. It might not be installed on your system; a `ls -lRa` (we recognize here the `ls -la`, the `R` is for Recursive) may suffice.

```console
.git
├── HEAD
├── config
├── description
├── hooks
│ ├── applypatch-msg.sample
│ ├── commit-msg.sample
│ ├── fsmonitor-watchman.sample
│ ├── post-update.sample
│ ├── pre-applypatch.sample
│ ├── pre-commit.sample
│ ├── pre-push.sample
│ ├── pre-rebase.sample
│ ├── pre-receive.sample
│ ├── prepare-commit-msg.sample
│ └── update.sample
├── index
├── information
│ └── exclude

│ ├── a7
```

We'll ignore the rest for now and focus on just one part:

```console
.git
├── index
├── objects
│ ├── a7
│ │ └── 8ab042d5f3b0a2369d27d60368fb2a2eada826
```

Here we have a very important file, `index`. And a directory structure of the form: `objects/<two letters>/<38-letter-filename>`. Don't worry if your object doesn't have exactly the same name, that's normal!
    
The **index** is the Git database. She tells him for each file that we want to follow (**Track**) where he is in life.

In **objects** is stored the actual contents of our work area files that have been added to the index or saved with a `commit`. Our "readme.md" has been put in a compressed form in `objects/a7/8ab042d5f3b0a2369d27d60368fb2a2eada826`.> :information_source:
> This weird file name is not random, it's a **SHA**. Git used what is called a "hash function" based on the contents of the file. Basically a hash function allows us to take content, no matter how small, and output a string of characters of fixed size (in our case 40 characters. Here the first two characters are used for the directory name and 38 for the file name).
> Changing a single character in the content completely changes the generated string. This is referred to as "addressing by content". When the content changes, the filename (hence or "address") changes.
> The hash function used is called **SHA-1**. And everywhere in Git, or almost, our identifiers will take this form. We are going to talk about **commit**, **commit-id**, **tree** and **tree-id**, **blob**s and all that, that we tell you will explain later, will always take a form like this: `a78ab042d5f3b0a2369d27d60368fb2a2eada826`. To make the thing a little more readable most often we will not use the 40 characters but only the first 7. So to talk about `a78ab042d5f3b0a2369d27d60368fb2a2eada826` we will rather talk about `a78ab04`, but that identifies the same thing.

Each file in our working directory can have three hashes in the index:

* One for its contents as it is currently in the working directory,
* one as it was when added to the index
* and one as it is saved, for real, in our repository.

If we run `git status` again, it will tell us:
```

```

that's it, Git is ready for us.#### Save a `git commit` milestone

In the terminal type:

```console
git commit -m"Added readme.md"
```

Normally Git will respond to us with:

```console
[master (root-commit) ec997c4] Added readme.md
 1 file changed, 1 insert(+)
 create mode 100644 readme.md
```

Here. It's done! We have saved a waypoint. You can type `git status`

Our **commit**. Forever from now on in the life of our project we will be able to go back in time, know what the content of the file was at that time, and we will also know who made what change and **why**.

> :information_source:
> We saw, when we typed the `git add` command it created the file in a compressed form in its ./objects/ directory and gave it a name based on the contents. So we lost the file name! Do not be afraid. In ./objects we have two other types of files that will allow us to find our file name: `tree` and `commit`.
Let's analyze just a little what we did ... and then, let's go into the details of what Git did. Indeed the `commit` command like the `add` command not only changes the index but also creates new objects in `.git/objects`

So `git commit` is the command that saves, and here we see for the first time one that has a mandatory argument: the `-m`. This argument indicates the **commit message**: the intention of our change. It's incredibly useful when working alone ("but why the hell did I do that! ah.. yes..") but it's even more important when working with others. In any case Git will refuse to save anything if you don't add a message.

> :warning:
> As someone who recruits quite a few developers, know that when I look at candidate code, I'm looking at commit messages as much as I'm looking at the code itself.

#### Save a second change then a third

We're on a roll so let's keep going! Let's make a second change. Open our "readme.md" with your favorite text editor and let's add for example:

```markdown
# My first Git project

Today we learned the following Git commands:

1. `git init` - initialize a new git repository
2. `git status` - find out the status of the working directory relative to the git repository
3. `git add` - add files to the git index to prepare for a commit
4. `git commit -m"{commit message}"` - save a milestone in the git repository
```

After saving the file, if we type `git status` again we will get a slightly different message.

```console
On branch master
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git checkout -- <file>..." to discard changes in working directory)

modified: readme.md

no changes added to commit (use "git add" and/or "git commit -a")
```

Great. Git is aware that the file has been modified.. and it even gives us directions on the next step. Let's go!

Again:
 
```console
git add readme.md
```

Then:

```console
git commit -m"Add the list of commands we learned today."
```

Who answers us with:

```console
[master 745866a] Add the list of commands we learned today.

 ```

> :information_source:
> Tip 1: if you get tired of typing `add` then `commit` each time, we have a shortcut: `git commit -am"my message commit"` the `-a` option added here, says **all* * ... Git will append all files tracked in the index that have changed to the commit. On the other hand, if a file has not yet been added for the first time, it is **Untracked**, it will do nothing for that one.
> Tip 2: if you have a lot of files in the directory and you don't want to add them one by one, you can add them all at once with `git add .` but be careful, often we have files lying around and that you don't necessarily want in your deposit. We'll see that later.

#### `git init`, `git add` and `git commit` summary

* `git init` - create a new, empty Git repository.
* `git add` - add a file from our work area to the index
* `git commit` - commit and save files as added to index
* `git status` - to see where we are. has the file been added to the index? Has it been modified since it was validated?
