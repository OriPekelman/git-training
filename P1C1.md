# Gérez et déployez votre projet avec Git

## Mettez en oeuvre un système de gestion de versions décentralisé

### Git, c'est quoi ?

Bonjour et bienvenue. Ce cours commence par un constat très simple : si vous voulez avoir un métier dans l'informatique, peu importe lequel, connaitre Git n'est pas optionnel ; Git est utilisé partout.

Tout d'abord. un mot sur le sujet, puis une petite explication du pourquoi.

Au plus haut niveau, on peut dire que Git est un logiciel qui permet de sauvegarder du code. C'est le standard absolu dans le domaine : la seule et unique manière de faire votre ctrl-s (ou cmd-s).

Vous pouvez apprendre à faire du HTML et du CSS (pour créer des pages web), à utiliser des langages de script comme Python, Ruby ou PHP pour créer des jolies applications web, du C ou du RUST (pourquoi pas pour créer votre propre système d'exploitation!)... Si vous n'avez pas une maîtrise minimale de l'usage de Git, vous n'avez jamais appris à sauvegarder votre travail. Ça serait dommage, non ?

Evidemment, si tout ce qu'il savait faire, c'était de la sauvegarde, ça serait la fonction de sauvegarde la plus bizarre et compliquée du monde et vous seriez en droit de décider que finalement l'informatique est une affaire de fous.

En réalité, c'est quelque chose de bien plus puissant: Git vous permet de sauvegarder votre travail, en gardant toutes les étapes intermédiaires de son élaboration. Imaginez un "ctrl-z" qui fonctionne à tout jamais, après avoir éteint sa machine...  qui fonctionne même quand on passe à un autre ordinateur. C’est puissant ça.

> On va y revenir... mais gardez en tête un premier mot technique : le "commit". C'est l'enregistrement d'un état de votre code, d'une version, d'un changement unique.

Mais Git est bien sûr bien plus fort que ça, il nous permet non seulement d'avoir un historique complet des changement et la manière de restaurer n'importe quel moment dans le passé.. il nous permet aussi d'avoir de multiples options différentes du même travail, en même temps.  Avoir deux, trois, milles pistes d'exploration, pouvoir basculer de l'une à l'autre, emprunter un bout d'idée d'ici, puis un bout de là-bas et composer ainsi votre version principale.

> Deux autres mots techniques d'abord la "branch": une version de votre travail, de votre code qui peut vivre en même que d'autres versions. Puis "merge" la possibilité d'apporter ou de "mélanger" les modifications faites dans une branche vers une autre.

Finalement et peut-être ce qu'il y a de plus merveilleux dans Git, la raison profonde pour laquelle vous devriez prendre ce cours au sérieux c'est que Git permet non seulement de sauvegarder votre propre travail mais aussi d'accéder à celui des autres, il vous permet non seulement d'avoir de multiples versions de votre code, mais aussi d'avoir des multiples personnes ayant chacune ses propres versions, ses propres pistes... et de constituer avec tout ça une seule version maitresse. Git permet une collaboration à une échelle sans précédent ; des milliers, voire des centaines de milliers de contributeurs qui travaillent ensemble pour créer une oeuvre unique. En effet Git est ce qu'on appelle un "système de gestion de version distribué" (et en Anglais: Distributed Source Control Management System). En gros vous pouvez sauvegarder votre travail en local, mais aussi pousser (en Anglais: "push") votre code vers un autre ordinateur qui aura alors sa propre copie indépendante du même projet.

> Derniers quatres mots techniques pour cette introduction : le **repository** ou le **dépôt de code** c'est l'entrepôt, le répertoire qui va contenir le code d'en projet, puis le "remote", qui est l'adresse d'un répertoire distant (sur un serveur sur internet par exemple, comme Github) qui va contenir une copie distincte du même projet. Push ou "pousser" nous permet d'envoyer notre code vers le **remote**. La commande **pull** (ou tirer) nous permet, à l'inverse, de télécharger du code depuis un dépôt distant vers notre machine locale.

Au tout début, j'ai déclaré que la connaissance de Git n'est pas optionnelle, et voilà pourquoi ; personne ne travaille dans son coin. Et la manière dont nous travaillons aujourd'hui ensemble dans le milieu informatique est totalement centrée autour de ce système qui nous permet de collaborer à l'élaboration de nos créations.

Git est jeune, il a été créé en 2005, mais en moins de 15 ans il s'est imposé comme le système majeur de gestion de code source, LE standard. Il existait bien sûr des systèmes similaires avant lui (CVS, SVN, SourceSafe) ; ils tendent à disparaître. Il existe d'autres systèmes modernes mais ils sont réservés à un usage de niche (Mercurial ou Bazaar). Il y a des gens qui bricolent leur propres petits systèmes (copier et renommer des répertoires de code en sauvegarde1, backup2, bk17 utiliser Dropbox, pourquoi pas un petit serveur de fichiers FTP) mais ceux-si ne peuvent plus espérer trouver un emploi dans le domaine ni avancer dans leur carrière.

Donc tenez bon. Allons-y !

> CADRE HISTORIQUE ET BONUS
>
> Git a été crée en 2005 par Linus Torvalds, le créateur de Linux, le principal système d'exploitation utilisé sur Internet. Il a créé Git pour remplacer un système propriétaire qui avait atteint ses limites. Linux, un noyau libre et open-source créé en 1991, a très vite gagné en popularité. En 2005 il était déjà composé de 6 millions lignes de code contribuées par 17,000 personnes.
>
> Linus a considéré que les systèmes qui existaient à l'époque étaient trop lents et inadaptés à cette échelle. Le système qu'il allait créer devrait être distribué, permettant le travail hors connexion, sans dépendre d'un système centralisé, rapide et collaboratif. Le tout début du système se composait uniquement des commandes de bas niveau, appelées les commandes de plomberie (en Anglais Plumbing), mais, avec le temps, Linus et les nombreux collaborateurs qui l'ont rejoint ont commencé à ajouter des commandes de plus haut niveau pour en simplifier l'utilisation (on se réfère à celles-ci en Anglais "Porcelain").
>
> Si à l'époque il existait de très nombreux sites web dédiés à l'open-source et des sites qui permettaient de publier du code source (tel sourceforge.net) ceux-si n'étaient pas faits pour la collaboration.  Le travail collaboratif se faisait par des listes de diffusion par e-mail, et par les groupes de discussion (Usenet); en 2018, le kernel Linux était toujours développé ainsi.
>
>Ces systèmes par email représentaient une énorme barrière à l'entrée pour les débutants et les contributeurs occasionnels. Aussi, l'imposition du Web comme la principale manière d'utiliser internet a poussé à une évolution des outils. En 2008, github.com est fondé. Ce site web commercial (bien que basé sur git, le code source du serveur n'est pas libre) permettait aux projets open-source d'héberger gratuitement leurs dépôts Git et exposait une agréable interface web pour voir le code ainsi que des fonctionnalités extrêmement simplifiées pour la collaboration. Il devient vite si populaire que des gens tendent à confondre Git et Github. Sa popularité a beaucoup baissé la barrière à la collaboration sur des projets open source et a aidé à imposer Git comme un standard universel. La très grande majorité des projets open source sont aujourd'hui sur github.com (même si l'auto-hébergement par des logiciels comme Gitlab commencent à avoir un deuxième essor); on y retrouve même un miroir du kernel Linux. La boucle est bouclée !
>
> En février 2017, Microsoft, l'ancien ennemi juré du monde du logiciel libre, a annoncé la migration du développement du code source de Microsoft Windows à Git. En juin 2018, cette société a annoncé l'acquisition de Github, scellant ainsi la prééminence de Git dans tous les domaines du développement informatique.

Glossaire Anglais à retenir:

1. Git - système de gestion de code source décentralisé
2. Repository - Dépôt de code Git, l'endroit où est stocké le code et son historique
3. Remote - l'adresse, la localisation, d'un dépôt de code Git sur un serveur
4. Commit - l'enregistrement d'un changement du code source d'un dépôt de code géré par Git
5. Branch - une branche, une version spécifique du code source - c'est une référence vers un "Commit" spécifique, des multiple branches peuvent coéxister dans le même dépôt Git
6. Pull - permet de recevoir du code dans son dépôt local
7. Push - permet d'envoyer ses propres changements, ses commits sur un dépôt distant
8. Merge - le mélange de des "branches" ou "commits" différents pour créer une nouvelle version ; la synthèse des modifications
