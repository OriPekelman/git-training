## Collaborer grâce à Git

Nous avons appris à sauvegarder notre travail en créant un dépôt Git. Puis comment suivre les changements de fichiers et de répertoires. Nous savons même repasser dans l'histoire, voir ce qu'on a changé.

Nous avons travaillé sur une seule branche de notre code (celle crée par défaut, **master**), et d'ailleurs rapidement elle est devenue un peu le bazar, mais nous avons appris aussi à revenir dans le passé pour faire du propre. 

Mais quand nous allons travailler avec d'autres ou même tout seul ceci n'est pas la bonne méthode. Assez souvent le travail de l'informaticien est exploratoire. On se lance sur une piste. On essaie un truc; Ca marche pas. On débogue. Ou on découvre qu'on peut faire mieux, plus propre. Et nous ne voulons pas passer notre vie à réécrire l'historique du dépôt, ni laisser à tout jamais chaque petit bout d'exploration. 

La vie est belle. Git est vraiment fait pour ça. Comme au tout début je vous l'ai raconté Git nous permet de travailler en même temps sur plusieurs versions de son code. La bonne pratique est de ne jamais travailler directement sur **master**. Et évidemment ne jamais réécrire le passé de **master** (ou toute autre branche qu'on aura partager avec d'autres).

### Collaborer avec soi-même. Les branches et leurs structures.

Chaque fois que nous allons commencer à travailler sur une nouvelle fonctionnalité ou sur la correction d'un bogue nous avons tout intérêt à créer une nouvelle branche. Ca sera notre espace de travail exploratoire où nous apporterons nos changements successifs. Quand nous sommes content de nos changements nous pourrions tout simplement le réintégrer dans le "tronc principal". 

Comment créer une branche?

#### Créer des branches

La commande `git checkout` que nous avons déjà vu nous permet non seulement de se mettre sur un autre commit.. mais aussi de créer une nouvelle branche.

```console
git checkout -b"my_new_feature"
```

Va créer une nouvelle branche branche à partir du commit sur lequel pointe mon **HEAD** et il va changer la branche courante vers celle-ci. Mais nous aimons comprendre ce qui se passe sous le capot .. n'est-ce pas. Jetons un coup d'oeil à notre répertoire `.git`.

````
.
...
├── HEAD
...
├── logs
│   ├── HEAD
│   └── refs
│       └── heads
│           ├── master
│           └── my_new_feature
...
└── refs
    ├── heads
    │   ├── master
    │   └── my_new_feature
    └── tags
```
Notre HEAD a changé. Si nous regardons à l'intérieur avec un `cat .git/HEAD` il dit: `ref: refs/heads/my_new_feature`, avant il disait `ref: refs/heads/master`.... et ça, c'est un raccourci, un lien, un pointeur vers un autre petit fichier qui vient d'apparaître.

Sous `.git/refs/heads` apparaît `my_new_feature`. Un coup d'oeil à l'intérieur: `cat refs/heads/my_new_feature` nous dit `120539df2817da4656c85af54061b06e15ae4b38`. Donc "HEAD" nous permet de connaître le "commit actuel". Quand il contient une référence comme `refs/heads/my_new_feature` ça veut dire qu'on est sur le haut d'une branche ("branch tip" an Anglais) appelé `my_new_feature`. 

Quand notre **HEAD** contient un **hash** alors on est dans cette situation de "detached head" que nous avons déjà vu, quand il contient la référence d'une branche... il va bouger avec le haut de cette branche. Ainsi si on ajoute maintenant un **commit** sur la branche `my_new_feature`, notre **HEAD** restera synchronisé avec celle-ci et il pointera vers notre nouveau **commit**.

> :warning: nous avons le droit de mettre pas mal de choses dans les noms de branches. Mais je vous suggère très fortement de vous limiter à l'alpha numérique avec des caractères toujours en minuscules avec `-`, `_`, `/` et `.` comme caractères supplémentaires tout au plus. Nous avons déjà noté que l'un des intérêts de Git ce qu'on peut l'intégrer dans pas mal d'automatismes. Plus vous serez baroques dans vos choix de noms, plus vous auriez une chance d'avoir quelque chose qui se casse.

#### Sauter de branche en branche `git checkout {branch_name}`

Rien de plus simple `git checkout master` va nous permettre de revenir à notre branche principale. Puis `git checkout my_new_feature` et hop on est revenue sur notre nouvelle branche.

#### Mais si j'ai fait des changements, puis change de branche, qu'est-ce qui se passe?

Vous pouvez être dans deux états. Soit on a déjà fait des **commits**, soit non.

##### On a fait un commit avant de changer de branche

Si on a fait un changement, et on l'a appliqué en faisant un **commit** avant de changer de branche: on arrive sur la nouvelle branche et notre zone de travail est mise-à-jour (on ne verra pas ce changement donc).

##### On n'a pas fait de commit avant de changer de branche

Si on a fait un changement mais on ne l'a pas appliqué avec un commit:

1. Soit aucun autre changement a été fait sur les mêmes fichiers .. et alors Git va mettre à jour la zone de travail pour ce qui n'a pas changé. Nos modifications vont encore être là.
2. Soit sur les deux branches il y a eu de changements sur les mêmes fichiers (donc on a fait un **commit** dans l'autre branche sur un des fichiers  ) que l'on a touché et Git va se plaindre. Il va nous dire "Hé! si vous voulez changer de branche il faut d'abord soit faire un `git commit` soit un `git stash`".

> :info_source_: Nous n'allons pas tout voir tout-de-suite; Mais sachez que `git stash` est une command forte utile. Parfois nous sommes au milieu du travail, on n'a rien encore commité. Et nous voulons aller voir ce qui se passe sur une autre branche. `git stash` nous permet de sauvegarder l'état actuel de notre zone de travail et de remettre celle-ci au propre. C'est un peu comme le `git reset` que nous avons déjà vu.. sauf que cette commande ne détruit rien. Elle place nos changements dans une zone-tampon (un peu comme le "presse-papier"). Nous pouvons maintenant aller voir ailleurs, même faire des commits sur d'autres branches... puis revenir à la notre, faire un petit `git stash pop` notre zone de travail aura de nouveau les changements qui étaient en course. On peut l'imaginer comme un "commit temporaire".


#### Comment suivre nos changements de branches? `git reflog`

Le **Reflog** est un mécanisme pour enregistrer quand la pointe des branches est mise à jour. Et la commande `reflog` permet de gérer les informations qui y sont enregistrées. En gros chaque fois que notre **HEAD** change, chaque fois qu'on ajoute un **commit** à une branche et donc que cette branche pointe vers un nouveau commit, Git enregistre ces changements. 

> :warning: vous allez vous emmêler les pinceaux plus qu'une fois avec votre apprentissage de Git... surtout quand vous allez commencer à utiliser des commandes plus poussées. Chaque fois que vous êtes perdus... souvenez-vous: un `git reflog` va souvent pourvoir vous expliquer ce qui s'est passé.

#### Visualiser les branches

Comme nous l'avons noté, la structure de branches est hiérarchiques. C'est un graphe. Notre branche **master** est la racine. 

Voyons un scénario d'exemple, imaginons que nous créons un site web ecommerce, et nous commençons à travailler sur le panier. Puis dans une sous-branche nous commençons à travailler sur son gabarit HTML. Ce travail est en cours, et entre-temps nous voulons revenir travailler sur notre page d'accueil.

Commencer à travailler sur la branche `shopping_cart` à partir du `master`:
```
git checkout master
git checkout -b "shopping_cart"
````

tap ... tap ...  tap, code ...  code ... code ... appliquer nos changements puis créer une nouvelle branche pour le gabarit:

```
git commit -am'Initial shopping cart code'
git checkout -b "template"

```
tap ... tap ...  tap, code ...  code ... code ... appliquer nos changements revenir sur master et commencer à travailler sur la page d'accueil:

```
git commit -am'Implement shopping cart template'
git checkout "master"
git checkout -b "homepage"
```

Donc si de notre branche **master** nous avoins crée une nouvelle branche `shopping_cart` puis de celle-ci une branche `template` et revenant à la branche master nous aurions crée la branche `homepage` nous allons arriver à la structure suivante:

```
- master
    -shopping_cart
        -shopping_cart
    -homepage
```

La commande `git branch -v` va nous lister les branches existantes ainsi que leur contenu. Comme nous avons déjà bien compris, le contenu d'une branche c'est simplement son dernier **commit**. Les branches dans Git n'ont rien de spécial. Ce sont simplement des synonymes de nos **commits**, quand on fait un nouveau **commit** dans une branche, cela veut simplement dire "mettre à jour la référence vers celui-ci".  Vous pouvez le vérifier en allant regarder à l'intérieur de `.git/refs/heads/`.

#### Récapitulatif,  les branches

* `git checkout -b"branch_name"` nous permet de créer une nouvelle branche, basée sur l'état actuel de l'index. Donc à partir du **commit** sur lequel pointe notre **HEAD**
* `git checkout branch_name` nous permet de changer la branche courante en mettant à jour le **HEAD** et notre zone de travail.
* `git stash` faire une sauvegarde de l'état actuel de nos changements dans la zone de travail qui n'ont pas été appliqués dans un **commit**
* `git stash pop` rétablir les changements sauvegardés par un `git stash`
* `git reflog` nous raconte ce que l'on a fait avec nos branches.
